# 函数的类型注解与模块导入

变量的注解写顺了手，函数这边还空着一块：参数和返回值。

函数是要给别人调的。调用的人通常不看函数体，只看签名——签名上不写类型，他就只能猜：这个参数该给整数还是字符串？返回的到底是一个值还是一堆值？猜错了，往往要等程序跑起来炸在某个运算上才发现。

先把冒号和箭头补进函数签名，让类型写在明面上；再顺着一个真实会遇到的报错——函数写在另一个文件里就是调不到——把模块和导入讲清楚。

## 冒号写给参数，箭头写给返回值

函数签名上有两个可写类型的位置：形参、返回值。

参数这一处没有任何新东西，写法和变量注解完全一样——形参名后面加一个冒号，冒号后面写类型：

```python
def analyze(scores: list[int]) -> tuple[int, int, float]:
    total = sum(scores)
    count = len(scores)
    average = total / count
    return total, count, average
```

`scores: list[int]` 里那个 `int` 不是"列表的类型"，而是"列表里每一个元素"的类型。列表本身的类型只有 `list`，中括号补的是元素这一层的信息：这个列表只装整数。少了中括号，等于只说"这是个列表"，里面装什么又回到靠猜。

返回值的位置要偏一点：不在冒号后面，而在参数列表的右括号之后。先写一根箭头 `->`（横杠加上大于号拼成），箭头后面写返回值的类型。

上面这个函数 `return` 了三个值。Python 里 `return a, b, c` 不是"返回三个值"，而是把三个值自动打包成一个元组再返回，所以返回值类型要按元组写，中括号里依次是三个元素各自的类型：总分 `int`、人数 `int`、平均值 `float`。顺序必须和 `return` 里一致——写成 `tuple[int, float, int]`，工具就会在你解包赋值的地方开始报警，因为拿 `float` 去接一个本该是 `int` 的变量，会对不上。

## 类型推断在这里为什么失灵

先看一段没写注解的代码，它根据半径算圆的面积和周长，返回两项数据：

```python
def circle(radius):
    area = 3.14 * radius * radius
    perimeter = 2 * 3.14 * radius
    return area, perimeter
```

Python 是有类型推断机制的，那它能不能把 `radius` 推出来？把鼠标放到函数调用处，看提示：`radius: Any`。

`Any` 就是"任意类型"，翻译成人话是"我没推出来，你自己看着办"。

推不出来的原因很直白：推断靠**值**去推。前面写 `a = 596`，一看是整数，`a` 就是 `int`；写 `flag = True`，一看是布尔值，就是 `bool`；做数学运算时也一样，靠参与运算的那个值来判断。可函数定义里的 `radius` 后面跟着值吗？没有。没有值，就没有推断的依据，工具只能给 `Any`。

有个小实验能验证这条规律：给形参补一个默认值，写成 `def circle(radius=10):`，再把鼠标放到调用处——推断出来了，是 `int`。因为默认值也是值，工具顺着它就能判断。

但这只是"恰好"。默认值的本职是让调用方可以省略参数，不是用来给工具递证据的；哪天默认值从 `10` 改成 `10.0`，推断出来的类型就跟着变，函数真正的意图反而没人写下来。

返回值那边通常不用操心：函数体里做的是浮点运算，工具顺着 `return` 的表达式就能推出 `tuple[float, float]`。所以返回值注解常常是"写不写都对"，参数注解却是"不写就没人知道"。

> **结论**：类型推断看的是"有没有值"，类型注解写的是"应该是什么"。形参没有默认值，推断必然给 `Any`，这时候注解不是锦上添花，而是唯一的信息来源。

## 圆的面积与周长：注解的即时反馈

把刚才那段圆的计算补上类型：

```python
def circle(radius: float) -> tuple[float, float]:
    area = 3.14 * radius * radius
    perimeter = 2 * 3.14 * radius
    return area, perimeter
```

半径标成 `float`，但调用时传 `10` 这样的整数不会有任何意见：`float` 能兼容 `int`，整数可以原样转成浮点数，一分不差。传 `10.5` 当然更没问题。

传字符串就立即翻脸。比如 `circle("10")`，写下去的一瞬间参数位置就标红了，提示的意思很明确：这里要的是 `float`，你给的是 `str`。

这就是参数注解最实在的收益——错误从"运行到乘法才发现"提前到"刚敲完就看见"。看见了就知道该改成浮点数，改完就对了，中间不用经历一次运行、一次报错、一次回头找。

返回值那处注解其实可加可不加，因为函数体已经能把它推出来。这里加上有两个理由：一是签名完整，工具在别处引用这个函数时不用进函数体去猜；二是读代码的人扫一眼箭头就知道，调完拿到的是两个浮点数，不是一个。

> **提示**：注解不改变程序的行为。解释器不会因为你在注解里写了 `float`，就在调用的时候拦住实参做类型校验——真正传错了类型，注解既不报错也不转换，最终出错的地方仍然是运行时的那次运算。它约束的是写代码时的工具提示，以及读代码的人对这份签名的理解。

## 订单金额计算器：让错误在写代码时就暴露

拿一段真写过的代码来收拾：一个订单金额计算器。它接收若干件商品，每件商品记成"名称、单价、数量"，另外接受优惠券、积分、邮费三项可选参数，最后算出应付金额。

它之前的表现很典型：把单价当成字符串传进去，写代码时安安静静，一运行就报错。这段代码要跑一次才知道哪里错了，这正是注解该解决的场景。

```python
def calc(*args: tuple[str, float, int],
         coupon: int = 0,
         points: int = 0,
         shipping: float = 0.0) -> float:
    total = 0.0
    for name, price, qty in args:
        total += price * qty
    return total - coupon + shipping
```

签名里有四个参数，类型来源分两种情况：哪些非写不可、哪些可以不写，也就清楚了。

后面三个参数都带默认值。默认值是 `0` 就是 `int`，是 `0.0` 就是 `float`，工具据此能推出来，注解可写可不写。这里仍然写上，一是正在讲语法，二是写上去之后，读签名的人不用回头去看默认值长什么样才知道类型。

真正非写不可的是第一个——带星号的那个。星号把调用时按位置传进来的实参统统收下来，打成一个元组；它没有默认值，推断给的是 `Any`。这一个不写，前面所有工作都白费。

它的注解要写两层的含义：冒号后面写的，是"这个大元组里每一个元素"的类型，而不是大元组的类型。这里的每一个元素是一件商品，本身又是一个三元组，于是写成 `tuple[str, float, int]`——商品名是字符串、单价是浮点数、数量是整数，顺序对应商品记录的顺序。

写对之后，把鼠标悬停在调用处，看到的是完整形态 `tuple[tuple[str, float, int], ...]`：外层那个元组是星号收集来的，里面每个元素都是内层的三元组。

> **易错点**：带星号的形参，注解天然是"逐元素"的。写 `tuple[str, float, int]` 说的是"收进来的每一样东西都是一个三元素元组"，不是"整个大元组恰好三个元素"。所以外面不要再套一层 `tuple[...]`，套上去意思就变成了"只有一个元素，而它是元组"。

注解一到位，两处错误当场现形：

- 把某件商品的单价写成字符串，`("商品", "18.5", 1)`，第二个位置立刻标红：这里要 `float`，给的是 `str`；
- 整条记录只写了三个裸数字 `(100, 99, 2)`，第一个位置标红：第一位应该是商品名，是 `str` 而不是 `int`。

返回值写 `-> float`。这一处工具给的推断未必可信——它顺着 `total` 的初值 `0.0` 和后面的减法走，给出的结果可能是个元组，而函数实际返回的就是一个浮点数。以真实的 `return` 表达式为准，写 `float`。

补完注解再回头调用，写错就有提示了：价格传整数可以（`int` 兼容进 `float`），传字符串不行；数量传 `2` 可以，传 `"2"` 不行。运行照旧，只是错误不再有机会溜到运行时。

四种位置的写法归到一张表里：

| 位置 | 写法 | 说明 |
| :--- | :--- | :--- |
| 普通形参 | `scores: list[int]` | 冒号后写类型；容器要写到元素这一层 |
| 带默认值的形参 | `coupon: int = 0` | 能推断，注解可省 |
| 不定长形参 | `*args: tuple[str, float, int]` | 写"每一个元素"的类型 |
| 返回值 | `-> tuple[float, float]` | 参数列表右括号后加箭头，多值按元组写 |

## 加与不加的取舍

函数的类型注解可以加，也可以不加。不加，函数照样运行，一个字符都不少算。

差别只在错误被发现的时间：不加注解，有些错误要等到运行时才浮出来，找起来还未必好找，代码的可维护性也就高不到哪去；加了注解，同样的错误在写代码的那一刻就暴露了，出错的概率自然降下来。

> **结论**：需要多人协作、要长期维护的项目，推荐加类型注解——省下的是后来人读签名、试参数的时间。工具能自己推断出类型的参数，加不加随你；推断不出来的（比如带星号的那种），建议加，否则它在签名上永远是个 `Any`。

## 一个跨文件的调用为什么报错

真实项目里不会把代码全堆在一个 `.py` 文件里。为了提高可读性和可维护性，代码会按功能和职责拆成若干个文件：算几何的放一处，跑业务的放另一处。

拆开之后，问题立刻来了。这里有两个文件，一个专门放圆的计算：

```python
# circle_function.py
def circle_area(radius: float) -> float:
    return 3.14 * radius * radius


def circle_perimeter(radius: float) -> float:
    return 2 * 3.14 * radius
```

另一个文件要算披萨的成本，得先按半径求出披萨的面积，于是很自然地写下这一行：

```python
# main.py
area = circle_area(15)
```

按道理这是同一个项目里的两个文件，函数名也没写错，应该能用。实际是：写下去就标红，鼠标悬停给出一句"未解析的引用"（unresolved reference）——说白了就是没找到这个函数；右键运行更直接，报 `NameError: name 'circle_area' is not defined`。

原因一句话能说完：`circle_area` 是在 `circle_function.py` 里定义的，`main.py` 里没有它。文件与文件之间不会自动通气——隔壁文件里写着，不等于当前文件里就有。

要让一个文件用上另一个文件里的东西，就得把那个文件当成"模块"导入进来。

## 模块就是一个 .py 文件

模块，英文 module。这个词听着比实际复杂：我们之前写的每一个以 `.py` 结尾的文件，本身就是一个模块。`circle_function.py` 是一个模块，`main.py` 也是一个模块。

模块是 Python 程序开发的基本组织单位。一个项目里可以有若干个模块，每个模块里都可以定义变量、函数、类，以及任何可执行的代码。这里的"类"要等面向对象那一章再拆开讲，眼下只用记住一句：一个 `.py` 文件就是一个模块。

自己写的这些 `.py` 文件，叫自定义模块。除此之外，Python 官方还准备了一大批内置模块，统称标准库，装好 Python 就能直接导入：

| 模块 | 用途 |
| :--- | :--- |
| `math` | 数学运算 |
| `random` | 生成随机数 |
| `os` | 操作系统相关信息 |
| `sys` | 解释器与系统参数 |
| `time` / `datetime` | 时间与日期 |
| `csv` | CSV 文件读写 |

一个项目里的模块关系，大致是这样：

```text
一个 Python 项目
├── circle_function.py     自定义模块：自己写的 .py 文件
├── main.py                自定义模块
└── 标准库（官方内置，装好即用）
    ├── math        数学运算
    ├── random      随机数
    ├── os          操作系统信息
    ├── sys         解释器与系统参数
    ├── time        时间
    ├── datetime    日期时间
    └── csv         CSV 文件读写
```

上半部分是自己写的，下半部分是官方随 Python 一起装好的——两者在使用方式上没有区别，都是先导入、再调用。

> **注意**：模块不是"存在就能用"。文件躺在项目目录里，或者标准库已经装好，都不等于当前文件里能喊出它的名字。要用哪个模块，先把它导入进来，这是硬前提。

## 模块带来的三点好处

官方把常用功能都封成了模块，做项目时缺什么导入什么，不必再从 0 到 1 造一遍。这件事的好处可以归成三条。

**提高代码的复用性**。常用功能已经被封装成一个一个的模块，要用的时候导入进来、调用一下就行，同一段逻辑不需要在第二个项目里重写一遍。

**降低开发的门槛**。Python 官方提供了大量内置模块，做一个项目不必把每个轮子都自己搓一遍。别人写好了、测过了，你直接调用——省下来的是开发成本，降下来的是入门的台阶。

**避免命名冲突**。所有代码都塞进一个文件时，起名是要动脑筋的：这个变量名有没有用过、这个函数名会不会和别处撞上，写的时候得一直提防。拆成多个模块之后，只要保证单个模块内部不重名就够了——不同模块里各叫各的，互不干扰。

所以在实际开发里，一个大项目通常是按功能、按职责拆成多个模块的。A 模块要用到别的模块的功能，导入进来就能用。

## 导入整个模块

导入的语法分两大类：一类把整个模块搬进来，另一类只从模块里取需要的功能。功能这个词范围很宽——可以是一个变量、一个函数、一个方法，也可以是一个类。

第一类最简单：`import` 后面跟上模块名。

```python
import random
```

`import` 就是"导入"的意思。想一次导入多个模块，模块名之间用逗号隔开：

```python
import random, os
```

这样整份模块就进来了，但用的时候不能只喊功能名，得带上模块名做前缀：模块名点功能名。因为导入的是整个模块，`randint` 这个名字并不在当前文件里，它住在 `random` 里面。

```python
import random

for i in range(100):
    print(random.randint(1, 100))
```

`randint` 生成一个整数随机数，两个参数分别是 start 和 end，也就是生成的随机数落在哪一段区间里。这里写 `1` 到 `100`，循环一百次，打印出一百个随机数——结果里既会出现 `1`，也会出现 `100`，两个端点都算在区间内。

模块名太长、后面要反复写的时候，可以给它起个别名，用 `as`：

```python
import random as rd

for i in range(100):
    print(rd.randint(1, 100))
```

`as` 后面的 `rd` 就是别名。一旦起了别名，模块名就换成它了——后面调用只能写别名点功能名，原来的 `random` 已经不认了。

> **提示**：在新文件里只是 `import random` 却还没用到它时，这句话会显示成灰色。这不是报错，是在提醒"导入了但没用上"。等下面写出一句 `random.randint(...)`，灰色自然消失。

## 只导入要用的功能

多数时候用不到整份模块，只要其中一两个功能。这时候换成 `from ... import ...`：`from` 后面写模块名（从哪儿来），`import` 后面写功能名（要哪个）。

```python
from random import randint

for i in range(100):
    print(randint(1, 100))
```

对比一下就能看出差别：调用时不再需要模块名前缀，直接写功能名。因为 `randint` 这个功能已经被单独取到当前文件里了，它不再需要靠 `random.` 来指明出处。

一次取多个功能，功能名之间用逗号隔开：

```python
from random import randint, choice
```

功能名太长也可以起别名，位置同样在功能名后面加 `as`：

```python
from random import randint as r_int

for i in range(100):
    print(r_int(1, 100))
```

起了别名之后，调用只能走别名——原来那个 `randint` 在这个文件里已经不再指代任何东西了。

还有一种偷懒的写法：把模块里的所有功能一次全取进来，`import` 后面写一个星号。这个星号是通配符，代表该模块中的所有功能。

```python
from random import *

for i in range(100):
    print(randint(1, 100))
```

全部取进来之后，调用时同样直接写功能名。

五种写法放在一起对照，区别一眼可见：

| 写法 | 导入的内容 | 调用方式 |
| :--- | :--- | :--- |
| `import random` | 整个模块 | `random.randint(1, 100)` |
| `import random as rd` | 整个模块，另起名字 | `rd.randint(1, 100)` |
| `from random import randint` | 一个功能 | `randint(1, 100)` |
| `from random import randint as r_int` | 一个功能，另起名字 | `r_int(1, 100)` |
| `from random import *` | 模块内全部功能 | `randint(1, 100)` |

> **结论**：调用方式只由一件事决定——导入的是整个模块，还是模块里的功能。整个模块进来，调用就得写"模块名点功能名"（起了别名就写"别名点功能名"）；功能被单独取进来，调用就直接写功能名（起了别名就写别名）。

## import 写在文件最上面

`import` 语句摆在文件的哪个位置，Python 不做强制规定。但约定俗成的写法是：整份导入语句放在文件最上方，具体的可执行代码放在它下面。

```python
# main.py
from circle_function import circle_area

area = circle_area(15)
print(area)
```

导入写在最上面，下面紧接着就是调用，读的人从上往下走一遍就明白这段代码依赖什么、又做了什么。这个习惯带来两个好处。

一是**依赖一目了然**。打开一个别人写的文件，扫一眼开头就知道它用到了哪些模块，不用通读全文去找。排查"这个项目到底依赖了什么"时，最上面那几行就是答案。

二是**顺序天然正确**。模块的操作一定是先导入、再使用，导入代码写在最上面，接下来的代码就都能直接用，不会写着写着突然发现某句话的位置不合适。

回到最开始那个报错：`main.py` 里调不到 `circle_function.py` 的函数，原因不是名字写错，而是没把那个文件当成模块导进来。补一行导入，两个文件之间的路就通了——模块负责把代码按职责分开存放，`import` 负责把它们重新连起来。分开是为了好维护，连起来是为了能用，两件事缺一不可。
