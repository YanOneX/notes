# 订单计算器与类型注解

购物车点下“去结算”的那一下，后台其实就是在做一道算术题：把车里每件商品的价格乘上数量，加总；再减掉优惠券、减掉积分抵扣；最后把运费加回来。题目本身不复杂，难的是它把函数参数设计里的几个坑一次凑齐了——商品有几件，事先不知道，优惠券和积分可能压根没有，参数一多还容易传错位置。

我们就用这个订单计算器，把不定长参数、默认参数、关键字传参这几样东西串成一个能跑的程序。等它跑通、测完，再回头看另一个更隐蔽的问题：代码里明明写错了类型，为什么工具一声不吭，非要等到运行才报错。

## 购物车结算：需求里有两条硬规则

要定义一个函数，接收三样东西——这一批商品的商品信息、优惠信息、运费信息——算出这批订单的总金额。

商品信息不是一件商品，而是一批。每一件商品至少要说清三件事：名称、价格、数量。这个“一批”是关键：购物车里放三件还是五件，写代码的时候并不知道。

优惠信息分两种：优惠券和积分抵扣。运费就是快递费。

两条规则，都是给优惠券和积分抵扣设的门槛：

| 优惠项 | 使用门槛 | 抵扣怎么算 | 上限 | 粒度 |
| :--- | :--- | :--- | :--- | :--- |
| 优惠券 | 商品金额满 5000 | 面额直接抵 | 不能超过商品总价 | 不限 |
| 积分抵扣 | 商品金额满 5000 | 100 积分抵 1 元 | 不能超过商品总价 | 只能整百 |

“只能整百抵扣”这句话得掰开说：兑换积分要一百一百地兑，不能几十几十地兑。这条规则看着只是句备注，写代码的时候它会决定你用哪个除号。

> **易错点**：两条规则里的“不能超过商品总价”，限制的是**抵扣掉的那笔钱**。优惠券是面额不能超过总价；积分要先换算成钱，再拿换算出来的金额去比。

## 三引号：注释还是字符串

需求先拿三引号粘到文件开头。粘完我愣了一下：同样是三引号，这段显示成绿色，而以前写的多行注释明明是灰色。

这不是编辑器抽风。Python 里根本没有单独的多行注释语法，三引号包起来的东西，本质就是一个字符串。它之所以平时能当注释使，是因为它单独成句、没被赋给任何变量，解释器执行到它直接跳过。习惯上我们就拿它当多行注释用。

颜色不同，是 PyCharm 在按位置和用途做区分：一个 `.py` 文件里第一个三引号字符串，它认为是描述整个文件功能的文档注释，标灰；后面再出现的三引号字符串，它当成普通的多行字符串，标绿。把上面那段剪掉，下面这段立刻变灰——它成了文件里的第一个。

> **提示**：灰的绿的都只是编辑器的着色，不影响运行，也不影响解释器怎么处理它。

## 定形参：不确定的数量交给不定长参数

写函数，先想形参。这一步想清楚了，函数体基本是照着往下写。

商品信息必须传。它是一批，件数不确定——个数不定，第一个该想到的就是不定长参数。而且商品是这笔订单的核心数据，用不定长位置参数最顺手，写成 `*args`。

后面三样是确定的：优惠券一个、积分一个、运费一个。

```python
def calculate_order_cost(*args, coupon, score, express):
```

命名上有段小插曲：`coupon` 这个词一时拼不出来，查了翻译才知道是它；`express` 取的是“快递服务”那个义项，别和“表达”混了。

参数定完，`args` 里到底装了什么？调用时每件商品传一个元组，`("鼠标", 188, 2)` 这样一个元组就是一件商品，传三件就是三个元组。`args` 本身是元组，里面套着若干小元组——外层是“一批”，内层是“一件”。

## 给函数写一份说明文档

函数名和参数名只说明了一半，还得写清楚每个参数期望什么。紧跟着 `def` 那一行下面，用三引号写文档字符串：

```python
def calculate_order_cost(*args, coupon, score, express):
    """
    根据传入的一批商品信息、优惠信息以及运费信息，计算订单的总金额。
    args: 商品信息，每一件商品包含名称、价格、数量三项，用元组或列表传入
    coupon: 优惠券金额
    score: 积分
    express: 运费
    return: 订单的总金额
    """
```

这段文档里最该写死的一句，是“每一件商品都要包含名称、价格、数量三项”。将来调用的人照这个顺序传，函数体里的下标才有意义。

## 把总金额拆成四步

写函数体之前，先把公式摆出来：

$$\text{订单总金额} = \text{商品总金额} - \text{优惠券} - \text{积分抵扣} + \text{运费}$$

注意最后一个符号是加。前面两项是折扣，运费是成本，性质不一样，很多人顺手就写成三个减号。

```text
商品总金额
   │  满 5000 才进入折扣环节
   ├─ 减 优惠券
   ├─ 减 积分抵扣（积分 // 100）
   └─ 加 运费
        │
        ▼
   订单总金额
```

读图：从上到下就是函数体的执行顺序。两个“减”都带前置条件，不满足就整段跳过；只有“加运费”是无条件执行的。四步对应四段代码，一步一段，出问题也好定位。

## 第一步：用列表推导式算商品总金额

商品总金额 = 每件商品的单价乘数量，再把每件的金额加起来。

先算每件的金额，收进一个列表：

```python
total_price = [goods[1] * goods[2] for goods in args]
```

`for goods in args` 遍历外层元组，`goods` 就是其中一件商品，一个小元组；`goods[1]` 取价格，`goods[2]` 取数量。两个一乘，得到这件商品的金额，列表推导式自动把它收进结果列表。

下标这里要留神：索引从 0 开始，名称是 `[0]`，价格是 `[1]`，数量是 `[2]`。凭直觉敲 `[2] * [3]`，轻则把数量乘到别的元素上，重则直接越界。

每件的金额都有了，累加：

```python
total_cost = sum(total_price)
```

`sum()` 把列表里的数全部加起来。到这里，这一批商品的总金额就拿到了，后面三步都在它身上继续做加减。

## 第二步：优惠券的两个条件

```python
if total_cost >= 5000 and coupon <= total_cost:
    total_cost -= coupon
```

两个条件缺一不可。商品金额满 5000 是门槛，优惠券金额不超过商品总价是上限，中间用 `and` 连起来，两个都为真才进分支。

`-=` 是复合赋值，`total_cost -= coupon` 等同于 `total_cost = total_cost - coupon`，扣完的结果还存回 `total_cost`，下一步接着往下算。

> **易错点**：只判断满 5000 就扣，等于允许一张一万块的券把订单扣成负数。上限那个条件不是凑数的。

## 第三步：积分先除以一百，再整除

积分抵扣的条件和优惠券长得几乎一样，但不能直接照抄。

```python
if total_cost >= 5000 and score // 100 <= total_cost:
    total_cost -= score // 100
```

照抄过来会写成 `score <= total_cost`，那就错了：4000 积分直接和几千元的订单金额比，等于把 4000 积分当成 4000 块钱。100 积分才抵 1 元，得先除 100 换成钱，再拿去比。

除的时候用 `//`，不用 `/`。规则说积分只能整百抵扣，`//` 是整除，除完不留小数；`/` 会算出 40.0、40.5 这样的浮点数，订单金额里就凭空冒出角分。“只能整百”这条规则，落到代码上就是这个双斜杠。

> **易错点**：判断条件和扣减金额两处都要写 `score // 100`。漏一处，要么拿积分原值和金额比，要么扣掉的是积分数而不是钱数。

还有一点：这里参与比较和扣减的 `total_cost`，是扣完优惠券之后的余额，不是最初的商品总金额。前一步改了它，这一步用的就是改过的值。

## 加运费、返回，再用两轮调用验证

第四步只有两行，运费无条件加，加完把结果交出去：

```python
    total_cost += express
    return total_cost
```

函数写完了，得验。第一次调用：

```python
total = calculate_order_cost(
    ("鼠标", 188, 2),
    ("键盘", 388, 1),
    ("手机", 3999, 1),
    coupon=10,
    score=4000,
    express=9.9,
)
print(total)
```

输出 `4772.9`。拿计算器核一遍：188 × 2 = 376，376 + 388 + 3999 = 4763。4763 没到 5000，两条折扣都不生效，直接加 9.9，正好 4772.9。

这一轮其实只走了一条路——两个 `if` 全都没进去。把手机价格改成 6999 再跑一次：376 + 388 = 764，764 加 6999 得 7763，过了 5000；减 10 得 7753；4000 积分换 40 元，减完 7713；加 9.9，7722.9。和输出对得上。

到这儿，条件成立和不成立两条路都跑过了。

> **提示**：测试最容易犯的懒，是只测“能跑通”的那一次。分支一个都没进去，结果看着漂亮，其实另一半代码从没执行过。

## 位置实参会被 *args 先收走

回看刚才那次调用，`coupon=10`、`score=4000`、`express=9.9` 为什么都带上了参数名？直接跟在商品后面写 `10, 4000, 9.9` 不行吗？

不行。四个实参全用位置传，鼠标往函数名上一放，提示就说形参 `coupon`、`score`、`express` 没有填。理由很直接：`*args` 是不定长位置参数，位置实参来多少它收多少，后面那三个也被它一并吞进 `args`，于是三个形参谁都没接到值。

两条路可选：

1. 把不定长参数挪到最后，写成 `def calculate_order_cost(coupon, score, express, *args)`。这样前三个位置实参各归各位，多出来的才进 `args`。
2. 保持现在的顺序，后面三个用关键字传参，明明白白写出“这个值是给谁的”。

我们选了第二种。商品是整笔订单的核心数据，让它排在前面更符合阅读习惯，而三个优惠类参数本来就该点名传。

> **结论**：形参表里一旦出现 `*args`，它后面的形参就只能靠关键字接值，位置实参在它这儿会被截胡。

## 默认值把可选参数补齐

再换个场景：这个账号既没有优惠券，也没有积分，只想付个运费。

那就只传 9.9。一运行，报错说缺少 `coupon` 和 `score`。定义时声明了形参，调用时不传，Python 不会替你猜一个值。

给它们配上默认值：

```python
def calculate_order_cost(*args, coupon=0, score=0, express=0.0):
```

没优惠券就是 0 元，没积分就是 0 分，免邮就是 0 元运费。传了用传的，不传就用默认值。三个参数一配齐，调用时只给商品也能跑。

加完默认值，`express=9.9` 那一处还会标黄：形参默认值写的是 `0`，属于 int；实际传进来 `9.9`，属于 float。这只是类型不一致的提示，不影响运行。嫌黄线碍眼，把默认值写成 `0.0`，上下都是 float，提示就没了。

到这儿，整个函数的定稿是这样：

```python
def calculate_order_cost(*args, coupon=0, score=0, express=0.0):
    """
    根据传入的一批商品信息、优惠信息以及运费信息，计算订单的总金额。
    args: 商品信息，每一件商品包含名称、价格、数量三项，用元组或列表传入
    coupon: 优惠券金额
    score: 积分
    express: 运费
    return: 订单的总金额
    """
    total_price = [goods[1] * goods[2] for goods in args]
    total_cost = sum(total_price)

    if total_cost >= 5000 and coupon <= total_cost:
        total_cost -= coupon

    if total_cost >= 5000 and score // 100 <= total_cost:
        total_cost -= score // 100

    total_cost += express
    return total_cost
```

三个优惠参数都有了默认值，最简调用就剩商品本身：

```python
total = calculate_order_cost(("鼠标", 188, 2), ("键盘", 388, 1), ("手机", 3999, 1))
```

这一版里，不定长参数、默认参数、位置传参、关键字传参四样全用上了：商品靠位置进 `args`，优惠参数靠关键字点名，没传的自动落到默认值上。

## 一次手滑：写的时候没人拦，跑起来才报错

再看那批商品数据。假设手一抖，第二件商品的价格敲成了字符串：

```python
total = calculate_order_cost(
    ("鼠标", 188, 2),
    ("键盘", "88", 1),
    coupon=10,
    score=4000,
    express=9.9,
)
```

编辑器一声不吭，没有波浪线，没有黄条。`"88"` 只是个普通字符串，语法上完全合法。

可一运行就崩，报的是 `int` 和 `str` 不能做加法。奇怪的是，明明写错的是“价格”，报错却出在加法上。顺着代码走一遍就明白了：`goods[1] * goods[2]` 是字符串乘整数，Python 允许，结果还是字符串 `"88"`；真正撞墙的是 `sum()`，它要把一堆金额加起来，加到一个字符串身上，才报出这个错。

> **结论**：错误出在离案发现场很远的地方，而写代码的时候没有任何东西能提醒你——因为 `args` 里每个元组该长什么样，代码里一个字都没说。

这就是那个不太好受的开发体验：写得对不对，只有当程序跑到最后一步才知道。能不能在敲下 `"88"` 的那一刻就被拦下来？能，前提是把类型写进代码里。

## 类型注解：在变量名后面加一个冒号

类型注解也叫类型提示，是 Python 的一种语法特性，作用是明确变量、函数参数、函数返回值的数据类型。

> **定义**：类型注解锚定在“数据类型”这一层——它声明的是这个位置将来存什么类型的数据，而不是这个位置存什么值。

写法很轻：定义变量时，在变量名后面加一个冒号，冒号后面写类型，等号照常赋值。

```python
a: int = 695
score: float = 98.5
hobby: str = "python"
flag: bool = True
pic: None = None
```

`a: int = 695` 读作“a 是 int，值是 695”。注解只负责说明类型，值还是由等号右边决定。以前定义变量是“变量名 = 值”，现在中间多插一段类型说明，语法位置就这么一个变化。

同一组变量，写与不写并排放着看：

| 存的数据 | 不写注解 | 写上注解 |
| :--- | :--- | :--- |
| 整数 | `a = 695` | `a: int = 695` |
| 浮点数 | `score = 98.5` | `score: float = 98.5` |
| 字符串 | `hobby = "python"` | `hobby: str = "python"` |
| 布尔值 | `flag = True` | `flag: bool = True` |
| 空值 | `pic = None` | `pic: None = None` |

冒号后面那个空格是规范，不是规定。Python 官方代码规范建议空一格，不空也能正常运行，只是看着挤。

## 容器类型与竖线

列表、集合、字典、元组也能注解，只是方括号里要交代元素是什么类型：

```python
names: list[str] = ["张三", "李四"]
phones: set[str] = {"13800000000"}
info: dict[str, int] = {"age": 18}
point: tuple[str, int, int] = ("鼠标", 188, 2)
```

- `list[str]`：方括号里写的是元素类型，这个列表里每个元素都是字符串。
- `set[str]`：同理，集合里每个元素都是字符串。
- `dict[str, int]`：括号里两个类型，前一个是键的类型，后一个是值的类型，所以这里键是字符串、值是整数。
- `tuple[str, int, int]`：元组按位置逐个写，第一个元素是字符串，第二个、第三个都是整数——正好对上一件商品“名称、价格、数量”那三项。

如果一个容器里要装多种类型，用竖线把它们隔开：

```python
names: list[str | int] = ["张三", 18]
```

`str | int` 读作“字符串或整数”。这个列表里放字符串也行，放整数也行，混着放也行。竖线就是 Enter 上面那颗键按住 Shift 敲出来的那个符号。

注解一写，提示立刻跟着变：往 `names` 里追加 `"王五"`，没毛病；追加 `10010`，也认；追加 `1.5`，波浪线就来了——因为 float 既不是 str 也不是 int。写代码的阶段就能看见“这里不对劲”，不必等到运行。

## 类型推断：不写注解，工具也知道

这里有个绕不过去的疑问：上面那些没写注解的变量，鼠标一悬停，怎么也能看到类型？

```python
a = 695
score = 98.5
names = ["张三", "李四"]
```

鼠标放到 `a` 上，浮出来的是 `int`；放到 `score` 上，是 `float`；放到 `names` 上，是 `list[str]`。和我们手写的注解长得一模一样。

因为 Python 有类型推断：它会根据代码推断出变量、表达式、函数返回值的类型。`695` 是整数，那么 `a` 就是 int；`98.5` 是浮点数，那么 `score` 就是 float；列表里装的全是字符串，那么 `names` 就是 `list[str]`。

推断的依据是赋给它的那个值，所以前提是“有值”。只声明一个变量名、不给任何值，就没有可推断的东西。

这也解释了一件事：直接赋值、参与运算、由容器推导出来的变量，类型注解都可以不写。工具推得出来，你写了只是把推断结果显式地钉在代码里。

## 注解只是提示，不是强制约束

注解写得再全，也别把它当成类型检查。

上面那个 `names: list[str | int]`，往里 `append(1.5)`，编辑器标了波浪线，明说 float 不在允许范围里。可右键一运行，`1.5` 结结实实地进了列表，`print` 出来它就在那儿。

> **结论**：Python 是动态类型的语言，变量的类型在运行时才真正绑定。类型注解只是多了一层提示，它不是强制约束，也不会改变 Python 是动态类型语言这个事实。

所以注解是可以不写的。前面写的那些代码一行注解都没有，照样跑得好好的；写了注解，运行时也不会因此多拦一道。

那还写它干什么？好处有三个：

1. 代码更清晰、更安全。类型写在明面上，读代码的人不必靠猜；很多错误在编写期间就能预见到，顺手就改掉了。
2. 代码提示更精准。工具知道这是个 list，就能准确列出列表常用的方法；说不清类型，提示只能给个大概。
3. 提前发现潜在问题。等号右边还没算完，编辑器已经能指出“这个位置不该放这种东西”。

顺着这个思路回头看最初那次手滑：`("键盘", "88", 1)` 之所以毫无阻拦，是因为那个位置没有任何类型信息可依。把类型写到代码里，工具才有对照的余地——它改变不了程序怎么跑，改变的是你发现错误的时刻：从运行之后，提前到敲下那一行的时候。
